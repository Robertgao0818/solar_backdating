开普敦装机日期回溯：Top-52 已产出，但外部校验未通过

生产管线干净地跑完了 21,453 个目标；卡住的是「我们怎么知道这些日期是对的」这一环。全城推广的前置条件目前尚未满足。

简报日期 2026-08-12 证据截至 2026-08-04 队列 ct_top52_tie_band_v1_20260724 普查截止 2025-01-31

核心判定

Top-52 的生产环节已完成且无运维缺陷，但验证环节失败：外部盲审与生产结果的精确区间一致率只有 20.8%，预注册门槛是 75%。更麻烦的是，这个「外部标尺」自己重复测两次也只有 68% 一致——所以目前我们无法判断到底是生产错了，还是尺子坏了。

它说明什么数据产品本身结构完整、可复现、精度不差（区间中位数 37 天）。缺的不是覆盖率或工程质量，而是一个可辩护的准确性上界。
为什么重要没有可信的参照物，就写不出误差界；写不出误差界，任何基于这批装机日期的经济学识别（事件研究、政策断点）都无法回应审稿人「你的测量误差有多大」这一问。
忽略的后果直接发布或直接推全城，等于把一个未知大小的测量误差按 5.2 倍规模复制到 111,801 个目标上，同时花掉不可回收的 API 配额、约 110 GB 磁盘和数日机时。

02

卡住的一关：CT-11 外部盲审四项闸门未通过

CT-11 的做法是：把生产给出的日期区间藏起来，用原生分辨率的影像条交给一个独立评审（Codex）盲判，看它给出的区间是否与生产一致。门槛在看到任何结果之前就被 owner 签字锁定（预注册，pre-registration，即先定标准再看数据，防止事后挪门槛）。结果是四项硬闸门未通过。

我把已冻结的对照表拆开看了一下分歧的结构——这是诊断，不是重新解释结果，失败的留出集仍然是失败的。

它说明什么。在生产明确认为「看到了跃变」的 325 个目标上，评审只有 12.3% 同意存在跃变，其余几乎对半分给了两个相反的绝对判断：49.2% 说「板子一直都在」，33.2% 说「板子从头到尾都没有」。更极端的是最后一行——在生产最有把握的「史前已在」那 51 个目标上，评审有三分之一说「根本没有板子」。

为什么重要。一个真正在测量的仪器，误差应该表现为在正确答案附近的抖动，而不是在两个相反极端之间对半开。这个模式与已记录的 68% 复评不稳定性是一致的：它更像评审在证据不足时被影像条的第一帧牵着走，而不是生产管线系统性地错了。所以现在的证据既不能宣告生产合格，也不能宣告生产不合格。

补充的坏消息。我另外算了一下：在生产与评审双方都给出了区间的 212 个目标里，区间中点的绝对差中位数是 187 天，只有 52.4% 落在同一年、31.1% 落在同一季度。也就是说，即使把精度要求放宽到「年度」这种经济学分析常用的粒度，分歧依然接近抛硬币。「门槛定得太严、其实产品够用」这条退路不成立——我本来以为它成立，数据不支持。

03

为什么修不动：四条低成本补救路线全部被否

按纪律，所有补救方案只能在已经失败的那 500 个上做开发和筛选，不许碰新封存的确认集（否则新集就被污染，失去一次性裁决能力）。08-03 到 08-04 试了四条，全部远低于 75% 门槛。

这四条否决的真实含义

它们不只是「方案不够好」。第三条（溯源规则只能到 52.1%）说明现有生产元数据里根本没有足够信息去预测评审的判断——所以「调阈值」「改状态机」这类便宜修法不是可行方向。第四条（冻结视觉骨干只到 56.3%）说明换更强的视觉模型也未必能跨过门槛。但这两条都有一个共同的替代解释：如果标签本身有 32% 的噪声（68% 复评一致率），那么任何模型的上限本来就在 70% 附近，四条全挂恰恰是「标签不可信」的旁证，而不是「任务不可能」的证据。这正是为什么下一步必须先修尺子，而不是继续换模型。

04

当前关键路径：人工校准包已冻结 8 天，无人评审

08-04 冻结了一个 100 个目标的人工校准包（ct11_human_calibration_v1_20260804/）：从失败的 500 里选，包含全部 32 个复评冲突样本，一目标一张原生细节图，盲发——不含目标 ID、生产结果、区间或旧标签。合约要求两位人类独立评审各自冻结一份 100 行结果，然后只对分歧行做仲裁，产出参照标签。

它说明什么。这是整条链上唯一还没被否掉的路径：先用人类标签判定到底是生产错还是评审错，再据此选补救方向。为什么重要。它现在是唯一的关键路径——CT-12 发布、封存确认集开封、全城推广三件事全部挂在它后面。忽略的后果。08-04 至今（8 天）没有新证据落盘，这 8 天是纯粹的日历损失；同时下游的全城下载正在消耗配额和磁盘，等待时间越长，「已投入但可能白投」的沉没成本越大。

05

下一步：全城推广的量级与前置条件

进行中 · 由另一 agent 执行

开普敦全城影像下载目前已在进行。这件事在排程上是合理的：下载与人工校准可以并行，能把等待窗口利用起来。但它与当前文档合约存在一处不一致需要处理——RUN-cape-town-ct11-corrected-qa-2026-08-03.md 与执行 tracker 里都明文写着「下游全开普敦 GEHI 取数/下载不得启动」。建议在 tracker 的执行日志里补一行 owner 决议，把它明确定性为「HOLD 期间授权的预取（prefetch）」，并写明预取不构成对 CT-11 的通过认定。这是文档诚信问题，不是技术问题：将来做审计或写方法附录时，会发现文档说不许下载而事实上下载了，那时无法自证是有意授权还是失控。

它说明什么。全城不是「多跑一会儿」，是 5.21 倍规模：六百万片影像、近三十万次 API 调用。为什么重要。磁盘那一行是硬约束——线性外推的 ≈110 GB 已经超过 97 GB 余量，而 Top-52 在配额窗口上就已经触发过两次 429 暂停。忽略的后果。下载跑到 80% 时磁盘写满，会以最难诊断的方式失败（部分写入的瓦片、半截的清单），并且届时已经花掉的配额无法退回。

需要在正式启动全城打分前补做三件事：（一）用 CT-only 的实际占用重算存储预算，而不是用混了 JHB 的 21 GB；（二）确认磁盘扩容或分层归档方案（Top-52 的瓦片是否可在打分完成后压缩/下线）；（三）按实测 2.57 次/目标和配额窗口重排波次计划——Top-52 六个波次用了约三天，全城线性外推是两周量级的机时。

  2. 2提交这 22 天的工作到 git 最后一次提交是 07-21，此后开普敦全部生产代码与文档（90 个未跟踪文件 + 29 个已修改文件，含全部 build_ct_*.py 与 RUN 文档）都只存在于工作区。这与项目「改变状态就要同步更新 tracker」的完成定义相冲突，且是纯粹的单点风险。成本几分钟，风险削减很大。 成本 低 · 风险削减 高

  4. 4人工标签到手后，先判定「谁错了」再选补救 两种结局的处理完全不同：若人工站在生产一侧，说明是评审工具不合格，需要重新设计参照物并重新预注册门槛（旧门槛作废但必须留档）；若人工站在评审一侧，说明生产管线确有系统性偏差，才需要真正的模型改造。现在做任何模型工作都是在赌一个还没揭晓的答案。 分叉点 · 决定后续数周的工作方向
